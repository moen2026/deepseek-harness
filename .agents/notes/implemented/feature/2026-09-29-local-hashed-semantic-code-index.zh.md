# Agent Note: 代码索引的本地哈希子词语义排序

Status: implemented

[English](2026-09-29-local-hashed-semantic-code-index.md) | 中文

## Problem

`search_codebase` 只用 BM25 排序：以分开的词表述的查询（"codebase search"）无法召回它从未逐字拼出的复合标识符（`searchCodebase`），因为 unicode61 分词器把标识符当作单个 token。用神经嵌入弥补这一缺口需要选定模型或端点，而仓库的既有中立性规则——DSH 不选定任何模型或嵌入提供方——加上离线"不安装任何内容、不访问网络"的契约都禁止这样做（[记忆决策](2026-09-27-opt-in-builtin-memory.zh.md)；提供方 README 的限制一节曾明确如此表述）。

## Decision

SQLite 代码索引提供方默认开启本地、确定性的语义排序（`semantic: true`）。索引时每个块经过对词 token、camelCase/缩写子词、相邻子词对与相邻词对的特征哈希投影；该投影做 L2 归一化并以 int8 量化存入逐块的 `code_vec` BLOB 表（schema 版本 2——旧的派生索引就地重置并重建）。查询时同一个纯函数嵌入查询，在向量表上做 JS 内余弦扫描得到第二个排序，并用倒数排名融合把它与 BM25 合并；纯语义命中（完全没有词法命中）仍会进入结果页。语义扫描只应用 glob/language 精化，绝不应用 MATCH 表达式，因为扩大词法命中集正是其目的。设 `semantic: false` 会把提供方退化为纯 BM25。

这是一个算法，不是模型：投影是文本的纯函数，不涉及权重、端点或网络，重建会产出完全相同的向量。因此中立性规则原封不动——DSH 仍不选定任何神经嵌入模型或提供方，且记忆提供方的外部端点向量路径（[记忆决策](2026-09-27-opt-in-builtin-memory.zh.md)）不变。

## Alternatives considered

**部署自带嵌入端点，如 memory 那样。** code-index 的配置面今天没有端点字段，而要求一个端点会破坏提供方"不安装任何内容、不访问网络"的契约；memory 包为需要真语义的召回质量保留了该路径。

**本地 ONNX 模型（如 MiniLM）。** 离线的真神经语义，但模型权重需要 vendoring，原生运行时会撞上供应链构建政策，也会改变"不安装任何内容"的承诺。

**子词感知的 FTS 分词。** 包装自定义 unicode61 分词器很脆弱，而且它仍然不能排序或弥合转述形态——只会扩大词法命中集。

**语义路径默认关闭。** 这会保留旧行为，但放弃了促成这项工作的零配置召回收益；该开关正是为想要完全旧排序的部署而存在。

## Consequences

- 在没有任何配置变更的情况下，间隔转述即可召回复合标识符；`semantic: false` 精确恢复先前的排序。
- 派生索引每块增加一个 128 字节向量（schema 版本 2）；v1 索引透明地重置并重建。
- 召回成本是每次查询对语料的一次线性 int8 点积扫描——在提供方的文件上限内为毫秒级——因此不需要任何 ANN 索引；融合路径上的命中分数是倒数排名融合分（提供方自定义单位），不是 BM25 值。
- 融合扩大了召回但不带来同义词理解；受影响 README 的限制一节描述的是子词形态的边界，而非"仅词法"。
