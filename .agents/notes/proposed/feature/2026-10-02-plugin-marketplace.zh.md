# Agent Note: Plugin marketplace catalog

Status: proposed

[English](2026-10-02-plugin-marketplace.md) | 中文

## Problem

今天安装一个 bundle 意味着把一个原始 spec——npm 包名、Git URL 或 tarball——敲进 Web 插件页、`plugin_manager` 工具或 `dsh plugin`。[注册表计划](../../implemented/architecture/2026-09-18-plugin-install-registries.zh.md)已经决定由哪个 registry 响应一个 spec，但没有任何东西帮助用户发现存在哪些 bundle。`inspect` 只回答包清单自带的字段，没有经过筛选的推荐 bundle 集合，没有评审过的版本，也没有在安装前阅读 bundle 内容的地方。想要提供受控目录的分发方——发放内部审定集合的企业、共享 profile bundle 的团队——只能用散文记录包名。

## Proposal

为插件管理增加一个可选的**目录源**：一个位于 URL 的带版本 JSON 文档，通常托管在 Git 仓库的原始文件中。目录列出经筛选的条目——包 spec、显示名称、类别、一个或多个钉住的已评审版本、许可证、可选的安全说明——并且只是数据：它从不托管代码，目录客户端在任何条目展示前先用 schema 校验文档。

客户端位于 `dsh-plugin-manager` 中，与既有 spec 操作并列。它用安装所用的同一代理环境抓取、缓存文档，并以过期提示代替默默提供旧副本。Web 插件页获得一个浏览已配置目录的界面；从目录条目安装走不变的 `inspect` 与 `installBundle` 管道，钉在该条目的已评审版本上。可以配置多个目录；默认不启用任何目录，没有配置目录的部署看不到任何新界面。

### Trust and review

目录的可信来自策展者而不是传输方式。条目钉住精确版本，使已评审的版本不会悄悄漂移；没有钉版本的条目在浏览界面中被标记，而不是与已评审条目同样呈现。策展者身份与评审流程是部署方的决策——格式承载字段，不承载策略。

## Alternatives considered

**托管的 marketplace 服务**，带搜索、评分与发布 API。暂时否决：它买下 DSH 并不具备的基础设施与审核所有权，而静态目录以近乎零的成本交付发现能力；目录格式应当是未来服务响应的子集。

**把 npm search 当作发现界面。**否决其作为唯一答案：所有已发布的名字都会出现，包括 typosquat，且没有任何东西区分经评审的 bundle 与任意的 bundle。目录策展才是这个特性。

**把一份出厂目录烘焙进应用。**否决：它在构建时给 bundle 集合打上日期戳，只有应用更新才能改变它；远程文档让策展者独立修订推荐。

**为目录条目换掉 pnpm、使用自定义安装传输。**否决：注册表计划刚刚加固了基于 pnpm 的安装（镜像回退、失败恢复文件、构建脚本审批）；第二个传输层要重新承担全部这些职责。

## Acceptance criteria

- 部署可以配置目录 URL 并在 Web 插件页浏览其条目；安装一个条目通过既有注册表计划产出普通 bundle。
- 钉版本的条目安装钉住的版本；未钉或过期的条目被明显标记，格式错误或不可达的目录降级为明确的错误状态，绝不回退到未评审的列表。
- 未配置目录时，所有既有界面的行为与今天完全一致。
- `plugin_manager` 工具可以列出目录条目，使 agent 能按请求浏览。

## Risks

通过受策展名字造成的依赖混淆，只能靠既有的私有注册表隔离与精确版本钉住来缓解；钉得松的目录会重新打开注册表笔记关上的那扇门。策展是工具无法强制的人类流程——目录的价值等于其评审纪律。Git 托管的原始文档有缓存与可用性怪癖，过期的目录可能宣传 registry 已不再持有的版本。
